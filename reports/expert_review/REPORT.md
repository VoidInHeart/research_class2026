# 先修主专家的参数，再判断是否需要第二位专家

2026-11-23 · SGD 离线研究 · `research/grounded-expert-review`

**有两项经独立确认的收益。** 在 2,193 条此前未评分的官方测试请求上，用对话证据纠正主专家参数，让完整正确数从 274 增至 328；只在提案缺必填项、无效或服务判断冲突时请第二位专家复核，再增至 347。前者每条仍调用一个专家；后者平均每条调用 1.183 位。分歧出现时，另一专家可以提供正确的整份方案。在本次资料中，两个专家分别贡献一个缺失参数的拼接没有带来可测的新增正确。[原方案与合并条件](PROTOCOL.md) · [正式测试成绩](test/results.json)

## 从上轮错例到可执行的改进

上轮的同意图分流在官方测试子集少答对 2 条，暴露出两个不同问题：有时工具已选对，但专家填错参数；有时请求的服务本身选错。回放**此前已经评分**的官方开发子集，815 条放行请求中，原矩阵选对服务与方法 476 次，只完整答对 188 次。其余 288 次中有 109 次漏填是否拼车；日期、目的地等也常有遗漏。不同错误可以发生在同一请求上。[历史错误计数](development_errors.json)

1. **单专家纠错**保留原专家及工具，只修参数。根据公共 schema 和对话中可定位的证据补查询日期、时间、城市、带单位的数量以及星级；遇到 `GetRide` 时识别用户明确提出或确认的拼车类型与目的地。直接使用原执行池的训练词典和日历资源，拒识仍然走一次兜底。
2. **条件双专家复核**先完成上述步骤。若提案无效、缺少必填参数，或冻结服务预测器给另一服务至少 0.50 分且领先主服务至少 0.30，则至多再问一位其他专家。服务冲突按工具是否为交易提名交易或搜索专家；若与主专家相同，则问上下文专家。单纯缺必填项优先问上下文专家。同工具时允许补入缺失的必填项；异工具时需独立服务预测支持，才替换整份提案。
3. **同预算整单交接对照**使用相同触发、相同第二专家，直接采用第二份纠错提案。另记录直接采用未纠错的原始第二提案。所有策略只生成一个最终工具调用；无 API、无外部工具副作用。实际部署不会预先运行所有专家。实验离线运行四路是为了给每条请求配对计分，回放程序会拒绝策略读取未经申请的提案。

## 数据边界

冻结原始意图留出、最近五条识别窗口、OOS 门控、主分支矩阵、三个专家和兜底。两批新样本来自同一固定版本 SGD 官方开发/测试分片；选择的是上轮整段排除的混合服务或混合意图对话。本轮只对**当前目标服务与方法仍在冻结目录内**的调用评分，隔离所有已评分对话、全部训练对话以及两个新集合之间的长短模板连通组。开发 1,756 条、1,092 段对话，放行 899 条；测试 2,193 条、1,513 段对话，放行 1,007 条。测试实际覆盖五个服务，开发七个；两组未知请求均为天气。入选以整段对话的混合性质为准，分别有 982 和 1,398 条在请求发生时的历史前缀已经出现过范围外活动。[独立隔离核对](cohort_audit.json) · [开发审计](dev/cohort.json) · [测试审计](test/cohort.json)

## 正式确认结果

完整正确要求服务版本、方法和整组参数都正确。下列百分比均以全部入选请求为分母；95% 区间按整段对话以配对方式重采样 2,000 次。

| 策略 | 开发完整正确 / 1,756 | 测试完整正确 / 2,193 | 测试准确率 | 测试专家调用总数 |
|---|---:|---:|---:|---:|
| 原矩阵，直接采用主专家提案 | 190 | 274 | 12.49% | 2,193 |
| 单专家参数纠错 | 225 | 328 | 14.96% | 2,193 |
| 条件双专家复核 | 229 | 347 | 15.82% | 2,594 |
| 同触发，整单采用纠错后的第二提案 | 232 | 364 | 16.60% | 2,594 |
| 同触发，整单采用未经纠错的第二提案 | 231 | 360 | 16.42% | 2,594 |

- **一次调用带来的收益**。测试中纠错救回 55 条，丢掉 1 条，净增 54 条，+2.46 个百分点，95% 区间 [+1.83, +3.14]；开发净增 35 条，区间 [+1.37, +2.67]。测试净增中的 49 条来自打车服务。唯一一次由对变错发生在 `test/21_00019:4`，纠错器将目的地后的拼车说明一并抄进了地址。由此可见，明确确认过的句子也可能含有多个不同槽位。
- **第二位专家的增量**。测试相对单修救回 20 条、丢掉 1 条，净增 19 条，+0.87 个百分点，区间 [+0.49, +1.29]；相对原矩阵净增 73 条，+3.33 个百分点，区间 [+2.64, +4.13]。开发相对单修净增 4 条，+0.23 个百分点，区间 [−0.11, +0.56]。两项达到原先规定的测试区间和开发方向标准。测试的 382 条未知请求中只有 26 条放行，复核和单修相对原矩阵均无完整正确数净增。
- **额外开销**。开发多问 280 次，测试多问 401 次，分别占全部请求的 15.95%、18.29%。测试每净多答对一条要额外出 21.1 份提案，开发为 70 份。按 ID 散列选取的 192 条测试请求上，真实执行三个方案各跑三遍，单机预热后，原矩阵/单修/双审的执行阶段 P50 分别为 1.67/1.66/2.20 ms，P95 为 2.98/2.96/4.55 ms。此计时起于共同的首选专家已选定之后，不含第一层识别，也不能直接外推到远程大模型。[开发全部配对结果](dev/results.json) · [测试全部配对结果](test/results.json) · [实际本地耗时](latency.json)

## 多专家的作用在哪里

在测试的 140 次高置信服务冲突中，复核让 73 条改用第二份提案，产生相对单修的全部 19 条净收益。例如 `test/15_00111:2` 要在 Lafayette 找美发沙龙，主专家误选活动查询，另一专家生成了正确的 `Services_1.FindProvider(city="Lafayette")`。也有反例：`test/32_00080:14` 原先正确的拼车调用被换成了歌曲检索。单看命中服务与方法，原矩阵、单修、双审分别是 978、978、1,016 条。

在另 261 次因缺必填项触发的测试请求中，保守复核最终完整答对 0 条。直接采用第二份纠错提案能答对其中 18 条。服务冲突子组中则是复核正确 21 条，整单交接正确 20 条。两者的专家开销完全相同，合计整单交接反超复核 17 条，但服务与方法命中数为 984，低于保守复核的 1,016；最终完整正确还取决于参数。这一对照解释了为什么“有帮助的第二意见”和“有帮助的融合规则”需要分开验证。

事后允许每条放行请求选择任一原始专家提案，测试最多答对 339 条。若在同一正确服务和方法内允许删去多余参数，再允许从最多两份原始提案中按槽组合，两个上限仍都是 339 条；开发对应为 229→232→232。在这两批数据里没有一条必须靠两份同工具原始提案分别贡献字段才能完整答对。双审实际答对 347 条能超过原始提案的 339 条上限，是因为文本纠错还能生成原始提案里没有的正确参数。以上上限未涵盖重新提取值、跨工具推断、自由文本协商或其他专家配置。[三种事后上限](opportunity.json)

## 整单交接的单独确认

整单交接在正式测试中以相同调用数胜过保守复核，因此在查看补充样本的策略成绩前又锁定一项确认。取旧 75 个训练分片中此前五折均未评分的混合对话，隔离全部既往拟合与评分对话、旧长短模板及整个官方开发/测试数据。在符合条件的 2,686 段对话中按事先固定的 ID 散列取前 1,000 段，共 2,032 条请求，1,233 条放行。覆盖 19 个服务版本，只有 52 条打车请求；25 条未知均为账户查询。这一人群与主要测试不同，结果单列。[补充方案](HANDOFF_PROTOCOL.md) · [隔离审计](transport/source_audit.json)

| 补充验证策略 | 完整正确 / 2,032 | 服务与方法正确 | 专家调用 |
|---|---:|---:|---:|
| 原矩阵 | 313 | 771 | 2,032 |
| 单专家纠错 | 342 | 771 | 2,032 |
| 条件双专家复核 | 343 | 782 | 2,427 |
| 同预算整单交接 | 349 | 755 | 2,427 |

整单交接对保守复核 6 胜 0 负，+0.295 个百分点，95% 区间 [+0.097, +0.543]；对单专家纠错 10 胜 3 负，+0.344 个百分点，区间 [0.000, +0.686]；对原矩阵净增 36 条，区间 [+1.189, +2.353]。第二项下界恰好等于零，未达到补充方案事先要求的严格正下界。整单交接保留在研究分支，主分支提供原方案中已通过确认的单修和条件复核。补充队列中保守复核相对单修也仅净增 1 条，说明第二次调用的回报随服务组成而变。[三个比较的逐项得失与区间](handoff_confirmation.json)

## 在主分支使用

已保存的 `retrieval-grounded` 运行目录和 `matrix` 策略支持三种 `--expert-review` 设置。默认 `off` 复现原行为，`single` 启用一次调用的参数纠错，`review` 在此基础上允许一次有条件的第二专家提案。新模式返回首位与第二位专家、提案次数、触发原因、处理方式以及最终调用；拒识仍只用兜底。已有本地模型运行目录可直接使用。例如从仓库根目录运行：

```powershell
python -m intentexec predict --run-dir artifacts/refreshed-existing-adaptive-run --policy matrix --expert-review review --text 'USER: Could you find a salon in Lafayette?'
```

实验代码、原始提案档案和复算入口完整保留在研究分支 `research/grounded-expert-review`；主分支收录已确认的推理实现及这次验证记录。在研究分支根目录、使用项目的本地 Python 环境运行：

```powershell
$env:OPENBLAS_NUM_THREADS='1'
$env:OMP_NUM_THREADS='1'
$env:HF_HUB_OFFLINE='1'
python -m intentexec.review_evaluation replay --cohort reports/expert_review/dev
python -m intentexec.review_evaluation replay --cohort reports/expert_review/test
python -m intentexec.review_evaluation replay --cohort reports/expert_review/transport
python -m intentexec.handoff_confirmation replay
python -m intentexec.review_opportunity
```
